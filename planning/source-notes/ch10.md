## 需要特別保持精確的技術邊界

1. **Send／Sync 與程式結果正確是不同問題。** 它們描述跨 thread 使用型別的安全契約，不描述任務完成、固定執行順序、公平排程或無死鎖。程式把計數讀出再存回，雖然每次都是合法 atomic 操作，仍可能遺失更新；這是邏輯問題，不能叫它 Rust 允許普通資料 race。
2. **`T: 'static` 不是要求值永不 drop。** 它排除 T 含有不足以支援該 bound 的借用；擁有自身資料的 String 可符合，仍可在 thread 完成時 drop。move closure 捕捉一個非 static reference，只是轉移 reference 值，不會延長 referent 存活。
3. **join 的 payload 與一般錯誤有不同角色。** panic unwind 下，join 能回傳 payload；panic abort 設定會終止 process，不會把所有 panic 化成可處理的 Err。若例子刻意 panic，需預先告知 panic hook 仍可能寫 stderr，即使 main 成功取得 Err。
4. **普通 spawn 與 scope 的 handle drop 語意不同。** 前者 detach；後者由 scope 在結束前等待。不能在說 auto join 時又推得任意背景工作都完成，例如 scoped thread 內另開普通 spawn 後 detach 的工作不在此保證裡。
5. **channel 的發送成功不是接收端已處理完成。** 成功代表 channel 接受值；receiver、worker 完成以及報告階段仍各有生命週期。根 sender 必須 drop，所有 cloned senders 才能共同形成「不再有新值」的邊界；buffer 需收完後才退出。
6. **Arc／Mutex 是不同維度。** Arc 維持 allocation 與 owner；Mutex 限制 inner data 的同時修改。Arc<RefCell<T>> 不能變成跨 thread 任意共享 mutable 資料的捷徑。
7. **poison 可以辨認某些中斷，但不是完整資料有效性證明。** 本章採「遇到 poison 回報工作失敗」作第一個可理解政策；若示範 into_inner，先列可檢查／修復的資料 invariant，不宣稱取得 guard 就已修好。
8. **用等待原因分析死鎖。** 主 thread 持有 guard 又 join 正等這把 lock 的 worker，彼此就無法完成。圖分清 lock 被誰持有與誰等誰；正文建議先 drop guard 再 join，而不把「少寫 lock」當萬能規則。

## 10.8 的有限實例與證明安排

本段只是作者方法設計，尚非已寫正文或已執行證據。

- **單一 counter：** 每個 worker 使用 AtomicUsize::fetch_add(Relaxed)，保留 handles，main join 全部之後才 load。理由分開：read-modify-write 避免丟更新；join 保證工作已完成並建立完成前後的同步邊界。Relaxed 不替 counter 附帶其他資料發布承諾。
- **一次發布兩個 atomic 值：** producer 先將數值寫入 AtomicUsize（Relaxed），再把唯一的 ready flag 寫成 true（Release）；reader 用 Acquire load 真正讀到這次 true，才以 Relaxed 讀數值。只有一個 producer、一次發布、不重設 flag，先列此有限契約。數值本身仍用 atomic，避免偷用 12 章才教的 unsafe／UnsafeCell。
- **先存證明再做測試：** producer 的數值寫入在 Release store 前；reader 的 Acquire 讀取從該 Release 取得 true；所以前後形成同步關係，數值讀取在其後，沒有其他寫入時應得到所發布值。若 flag 改用 Relaxed，失去的是跨變數的這條保證，不能用「本機仍讀到 42」反推沒有差異。
- **圖：** 兩條有明確方向的 thread 軌跡，各列數值寫入／flag Release、flag Acquire 觀察 true／數值讀取。粗橫向箭頭只代表這個讀取觀察該 store 所形成的同步，不用普通時間軸誤示所有實際事件有全序。
- **操作組合：** load 可用 Relaxed／Acquire／SeqCst；store 可用 Relaxed／Release／SeqCst；read-modify-write（例如 fetch_add）才容納 AcqRel。Acquire 的 read-modify-write 寫入側是 Relaxed，Release 的讀取側是 Relaxed。若不實際教 compare_exchange，本章不突然展示 success／failure ordering 的雙參數。
- **SeqCst：** 交代它額外建立所有 SeqCst atomic 操作共同遵守的順序，不等於所有普通操作都在同一條直線執行，也不替多步 transaction 自動加 lock。可用有限兩旗標模型辨認允許／禁止結果；不以實測特定硬體是否碰巧出現結果作證明。
- **讀者驗證：** 有限 counter 結果與一次發布結果可測；再要求讀者在圖上指出必要 edge、解釋刪去某個 ordering 失去何種保證。測試可發現程式或不變條件錯誤，memory-model 契約的理由另存。Loom 的執行模型與工具契約留 14.6，不讓它成為本節理解同步的唯一來源。
- **忙等範例：** 若需要輪詢，只在數行一次發布的示意內，先教 thread::yield_now 行為和不保證公平排程的限制。正文提示真實等待通常用已學 channel／lock 表達，避免把忙等當完成任務的通用寫法。不在本章先加 Duration／Instant。
