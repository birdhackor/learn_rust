## 受控驗證的寫作決策

以下是作者後續的安排，不是已驗證範例，也不能交给首次閱讀者作提示。

1. 11.1 用無外部網路的最小工作看出「呼叫先得到 future，await 後才得到值」。在程式前教 `#[tokio::main]` 的展開角色、runtime／features；不用有 Pin 簽名的 Future 完整定義補洞。
2. 11.2 區分工作錯誤與 task failure，逐步教 JoinHandle／JoinSet／task Id。能以受控 channel 卡住工作，再發訊息讓它完成，不需靠 sleep 猜 task 已啟動。
3. 11.3 用開始／允許完成的事件證明至多 jobs 個工作，而不是只量整體秒數。控制訊息的容量、send／recv 與所有 sender 的 ownership 必須先交代。
4. 11.4 timeout 可包住沒有放行的 channel 等待，以不同可控制操作呈現正常／逾時兩類，不把 CPU busy loop 當可被強制中止。Duration 的單位、Instant 的時間點／elapsed 與 deadline 範圍在使用前教。
5. 11.5 每次等待只用 cancellation safe 的接收與取結果；收到 stop 後停止補新工作，abort_all 後完整 join；保留已完成結果，不把所有仍在集合的 task 一律覆寫取消。正常輸出、task failure、取消／未開始有不同身分与後續用途。
6. 11.8 先從最小回應服務增加狀態、redirect、受控延遲與計數，每次只加一個主要需求。動態 port 的 listener 取得成功是 listener readiness；如果需要 HTTP handler 已能回應，用真正健康回應或事件確認，不靠固定 sleep。
7. 本機 fixture client 要在程式前教 `ClientBuilder::no_proxy()`，避免執行環境代理改變測試對象；一般使用者 client 繼續尊重環境代理。這是 fixture 路徑的具體必要差異，不要求教整套 proxy 配置。
8. 受控延遲 endpoint 若還等 release gate，graceful shutdown 會等尚在服務的 handler；fixture 收尾需先釋放 gate 或明確另行取消並等待，不能只 send stop 後宣稱立即收尾。
9. B 專案後來會以 input index 排序；本章先教 task完成順序與 task Id，再教輸入身分 mapping，保證 task failure 也可對回原項目。
