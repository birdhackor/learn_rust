## 1. Alias、tuple struct 與單位邊界

1. **是什麼／與前文關係（explained）**：`type MeterAlias = i32` 與 `SecondAlias = i32` 都只是既有 i32 的別名，不能使公尺和秒分開。原文說「newtype pattern」是設計方式而非關鍵字；`pub struct Meters(pub i32);` 的 tuple struct 才建出新型別，`Meters`、`Seconds`、i32 互不相同。這沿用前文 struct、pub 與所有權。
2a. **機制／性質（explained）**：欄位按位置，以 `Meters(80)` 建立、`.0` 取第一欄；兩個 pub 各控制型別和欄位的可見性。derive Debug、PartialEq 沒有 derive Copy，因此整個 Meters 仍會 move；內層 i32 可以 copy 不會使外殼自動 Copy。別名指向同一型別，例中的 `PriceFn = Box<dyn Fn(i32) -> i32>` 可直接交給完整拼法而不重新配置或 clone。
2b. **需要／用途（explained）**：`distance_value(&Meters)` 拒絕 `&Seconds`，所以單位錯誤能在編譯時發現；別名主要縮短拼寫，不能提供這個保證。公開內欄只保證單位身分，沒有範圍驗證。
3. **怎麼用／輸入輸出（explained）**：用 `Meters(80)` 建值，傳 `&distance` 給 `distance_value` 得 i32 80，原值仍能 Debug 印出。`PriceFn` 接 i32 回 i32；discount=true 的 80 得 70。
4. **例子能／不能說明（explained）**：同頁 E0308 顯示不同 newtype 的參考不能互代；alias 範例則讓秒值被距離函式接受，說明漏洞。不能由名稱推論公尺一定非負，亦不能推論 tuple struct 有額外 heap 配置。

我的小變化預測：`Meters(-1)` 在目前公開欄位與沒有驗證的定義下仍可建出；若只是把 i32 改叫另一個 alias，仍不能阻擋混用。這是由目前定義推得，未實跑。

## 2. Add、預設型別參數與 associated Output

1. **角色（explained）**：原文以 `std::ops::Add` 對應 `+`；`Add<Rhs = Self>` 的 Rhs 是右運算元型別，省略時為 Self。這是「預設型別參數」，和 11.7 trait 方法有預設實作不同。`Output` 沿用 associated type 概念，決定加法結果。
2a. **機制（explained）**：`add(self, rhs: Rhs) -> Self::Output` 取得兩邊所有權，非 Copy 的 Meters 會 move。`impl Add for Meters` 選 Output=Self，實作把兩個 `.0` 相加再以 `Self(...)` 建回單位值。`impl Add<Meters> for Millimeters` 只授權左 mm、右 m 這個方向，內部將右值乘 1000；不自動生成反方向或其他運算子。
2b. **用途（explained）**：讓單位換算和可用的運算方向成為型別介面。`add_same<T: Add<Output = T>>` 除了要求可以相加，還明說結果必須與 T 相同，因為單有 Add 並不保證 Output=Self。
3. **用法（explained）**：Meters80 + Meters120 → Meters200；`add_same(Meters(40), Meters(60))` → Meters100；Millimeters500 + Meters2 → Millimeters2500。用過 left+right 後不能再用非 Copy 的 left；要保留原輸入須另外選借用介面或合適的 Copy 設計。
4. **例子界線（explained）**：E0382 與反向相加 E0308 分別展示 move 和未提供 RHS 實作；沒有示範溢位政策，不能推論自動安全換算或隱藏 clone。

我的小變化預測：即使 `Millimeters + Meters` 有效，`add_same(Millimeters(500), Meters(2))` 仍不符合兩個輸入同一 T 的簽名。若一種型別的 Add 結果是另一型別，也不滿足 `Output = T`。此為簽名推論，非隔離測驗。

## 3. Local wrapper、orphan rules 與公開介面

1. **角色（explained）**：原文用 Display Vec 的需求引出 orphan rules；「local」是 trait 或型別定義在目前寫 impl 的 crate，不是 import 到目前作用域。nongeneric 的 `impl Display for ...` 至少 trait 或 self type 一個需 local。
2a. **機制（explained）**：替 Vec<i32> 取 `CountList` alias 不會改變它和 Display 都屬外來定義，E0117 仍拒絕。新 `MeterBatch(Vec<Meters>)` 才是本 crate 的型別，可為它 impl 外來 Display；反過來，本地 BatchSize trait 可 impl 給外來 Vec<i32>。inner Vec 私有，wrapper 不會自動繼承 Vec 的 push，未實作 Deref。
2b. **用途（explained）**：原文給的理由是避免不同函式庫為同一外來 trait/type 定義互相衝突的 impl。wrapper 同時選擇公開契約，這裡只承諾建立、計數、總和、顯示；沒有必要把全部 Vec 方法露出來。
3. **用法（explained）**：`from_values(Vec<Meters>)` 接走 Vec，無額外 Box/clone；`count(&self)` 回 usize，`total(&self)` 借用 slice、加總內層 i32、回新的 Meters。Display 借用而輸出「2 段路程，共 200 公尺」，顯示後還能 total。
4. **例子界線（explained）**：E0599 顯示沒有 push；不是證明 wrapper 永遠不能設計 push，而是目前公開介面沒有它。完整程式與空 batch 測試顯示總和 0，但沒有長度上限或溢位保證。

我的小變化預測：只 use 一個外來 trait 或再替 Vec 取新 alias，都不會讓 orphan 判定變 local。增加另一個本地 wrapper 也不會自動取得 Copy 或 Vec 方法。

## 4. Generic orphan 順序、uncovered parameter 與 fundamental types

1. **角色（explained／有限理解）**：generic 外來 trait impl 還要沿 self type、再 trait 型別參數的順序檢查；第一個 local type 之前不能出現 uncovered type parameter。這補充前面 nongeneric 的簡化規則，不能只找某處有 local 型別就通過。
2a. **機制（explained）**：`impl<T> From<T> for Wrapped<T>` 的 self type Wrapped<T> 已先是 local，合法；`impl<T> From<Wrapped<T>> for T` 卻先見裸 T，再見 local Wrapped，E0210。原文另指出 fundamental 類型有特殊待遇：Box<LocalType> 可算 local，而 Box<T> 不把 T cover；普通 Vec 可以 cover T，但 Vec<LocalType> 不因此算 local。
2b. **用途（explained）**：解釋 generic 轉換的授權邊界與編譯診斷；不是讓每個外來 self type 一律禁止，也不是讓 local type 放在任意後方就足夠。
3. **用法（explained）**：`80.into()` 在目標標成 Wrapped<i32> 時得到 wrapper；Wrapped::from 接走 String，固有方法 `into_inner(self) -> T` 把內值取回。into_inner 沒有替任意外來 T 加 foreign trait impl，因此不落入那個反向 From 限制。
4. **例子界線（explained／missing 操作熟練）**：有完整合法 From、反向 E0210 與 String move-out；fundamental/Vec 規則只有文字說明，沒有獨立 impl 範例。能重述上述差異，尚不能聲稱可獨自判斷所有多參數／巢狀組合；未用後文補答案。

我的小變化預測：把合法 `.into()` 的目標型別提示移除且沒有其他上下文時，無法只靠來源 80 保證一定選 Wrapped<i32>；先前型別推論仍需要目標依據。未實跑。

## 5. Coherence 與 blanket implementation 重疊

1. **角色（explained）**：coherence 同時要求 orphan 合法和沒有重疊；blanket implementation 指 generic impl 涵蓋一整類型別。這是另一個判斷軸，不是 local trait 就可覆寫。
2a. **機制（explained）**：`impl<T> Label for T` 已含 Meters，再加 `impl Label for Meters` 會使同一型別有兩個適用 impl，E0119。編譯器沒有依「更具體」自動挑後者。
2b. **用途（explained）**：確保某型別使用 trait 方法時有唯一適用實作。若要各型別不同標籤，不能先宣告所有 T 一律採共用版本。
3. **用法（explained）**：在設計 impl 前分別問誰有權實作，以及適用集合是否相交；此頁沒有教覆寫或 specialisation 用法。
4. **例子界線（explained）**：本地 Label 的 E0119 證明重疊仍被拒絕；不能推論本地 trait 無法為不同互斥型別各自實作。

我的小變化預測：若移除涵蓋所有 T 的 blanket impl，只保留 Meters 的 Label，這一對重疊來源便消失；其他未列的 impl 是否衝突仍須另查，本文未給它們。
