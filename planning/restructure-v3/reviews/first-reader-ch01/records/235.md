# 235 — A 待回時先做 B

無PNG／新API，未執行。本包具體化232預覽，不借未釋出實作說明。

1. **what（explained）**：同一thread保存A未完進度，在A等回覆期間讓獨立B前進，仍需A+B才report；沿既讀concurrency是工作期間重疊，非一定同時算。
2a. **機制／性質（explained到安排；保存方式deferred）**：原文四步發A/保存未有結果→同一路徑B200→若A沒回仍等→回覆來再處理取3。只需A期間含等待、B在期間進展，不需兩段計算同刻執行；怎用Rust保存進度仍沒講。
2b. **why（explained）**：能利用的是「B 不依賴 A」，不能靠切換消除資料依賴。B若計庫存3件價格，須先知3。
3. **how（explained情境）**：同樣輸入得相同庫存3／合計200，變的是安排；B完若沒有其他可做仍需等，並非async使外部回覆即時。
4. **例子界線（explained）**：這可辨認單thread的concurrency，不證明parallelism或任何速度；沒有聲稱倉庫查詢已用Rustthread。

小預測：若把B改成80×庫存數，不能在未知A時算出最終價格；仍可做其他不依A的部分，但本例沒有給這種額外工作，不自己編成作者原需求。未跑。
