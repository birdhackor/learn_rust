## Atomic 值、RMW 與回傳

1. **what（explained）**：atomic相對同一位置其他atomic不可拆，AtomicUsize存usize、AtomicBool存bool。Send/Sync且sharedreceiver內部更新，owned本身非Copy；Arc分發同一位置owner，不是多獨立counter。
2a. **mechanism（explained）**：new設初；load交普通Copy值，store替換而非加；fetch_add將讀舊/加/寫合成read-modify-write，回舊值。overflow採wrapping、不因debug自動失敗，和前文普通整數檢查政策有別。order取atomic::Ordering enum，不是cmp::Ordering比較結果。
2b. **why（explained）**：各工作完成一件安全加同counter，避免兩路徑分開讀改寫丟一次更新；不需為這一數字持整份guard。
3. **how（explained）**：80.fetch_add120→old80、load200，store230再load230。move AtomicUsize給second後first再讀E0382，但old仍普通80。單thread例只核API值，不測速度。
4. **examples（explained）**：受控load0/load0/store1/store1最後1是lost update，不偽裝真thread頻率；每存取atomic無data race仍可業務錯。SeqCst也不把分開五步合一，正確增加用fetch_add或Mutex整段。

小預測：store(1)兩次仍是1，fetch_add(1)兩次從0則2；不把「每個操作atomic」推「多句話一體」。未跑。

## Relaxed 的同位置順序與 join 同步

1. **what（explained）**：Relaxed保各單步atomic及同一atomic修改順序各thread一致，不同步不同atomic，也不保每次load立即最新／通知。join這頁新增明說記憶體同步邊界，不只等待。
2a. **mechanism（explained）**：同counter每fetch_add讀修改序緊前值加1。worker完成前操作happens-before join返回後操作，兩份都join後無未完成／後續寫，Relaxed final load須讀5。不是Relaxed自己突然變跨位置發布。
2b. **why（explained）**：RMW管一次更新不丟，join管全部完成後何時讀，分開證明；只見count5不順便證另一模型已發布。
3. **how（explained）**：兩Arcclone worker各3/2次fetch_add，兩join皆Ok才load驗5，任panic不當完整五件。
4. **examples（explained）**：同counter、只有五次+1、無其他寫無overflow是理由前提；不是任何Relaxed load都能直接說一定最新。未執行。

小預測：若多第三worker再一次+1，只有把其handle也join並確認正常、無其他寫，才沿相同理由讀6；若漏等不能以原五次例硬保最終6。有限變化推論未跑。

## Memory model、happens-before 與唯一發布

1. **what（explained）**：memory model定可依契約，happens-before可串接先後，不是量時間或替全程所有操作畫共同時間軸。Release寫、Acquire讀可建立跨thread同步，但必須讀自同一atomic那次Release。
2a. **mechanism（explained）**：限定DATA0/READYfalse、一producer一次DATA230再READYtrue、無重設／後寫。P1 DATA.storeRelaxed→P2 READY.storeRelease；R1 READY.loadAcquire讀到P2true→R2 DATA.loadRelaxed；P2同步R1，串P1→P2→R1→R2。已HB的讀需見那次或更後修改，無後寫所以230。
2b. **why（explained）**：看到「可讀」旗標需要一起發布已算完資料，不是兩個獨立變數剛巧先後。只有order名字湊一對、讀別位置或別次更新不足本例推理。
3. **how（explained）**：Arc tuple0DATA/1READY，producer兩store，main Acquire讀true才Relaxed讀DATA，然後才join。晚join只收尾、不能倒替較早讀解釋；兩邊之一改Relaxed少同步承諾，見true而DATA0是模型允許，不靠我本機一定發生。
4. **image（explained）**：PNG頂「唯一一次發布」，左藍P1DATA230Relaxed向下灰到P2READYtrueRelease，右綠R1READYtrueAcquire向下灰到R2DATA230Relaxed；跨欄藍箭頭旁「R1讀自P2才形成同步」，底串P1P2R1R2。兩欄是同共享位置，圖僅畫true那次，不將先前false讀也配對。不是物理時距、非兩份各自資料。

小預測：若producer在Release後再改DATA，原HB仍只覆發布前寫，不能沿原理由保R2一定230或多欄同批；不等說每次一定錯。若讀到false，不能當本次完整成果。未跑。

## Yield、busy-wait 與值正確不等有期限進展

1. **what（explained）**：yield_now無參數回unit，告OS願交執行時段，不保哪工作下個或公平；反覆檢查可能busy-wait耗CPU。
2a. **mechanism（explained）**：while未Ready就yield，值協定保讀true時可用230，卻不保producer何時排到或輪詢固定時間停。若producer失敗未發布，單旗標沒關閉／錯誤協定，consumer可一直等。
2b. **why（explained）**：這有限例隔離Release/Acquire，而一般事件等待先考慮既讀channel／join／鎖；yield不是建立同步關係的來源。
3. **how（explained）**：while !READY.loadAcquire {yield_now()}，退出才讀payload再join。publisher合法兩store後不再改；只讀到payload還須join分正常return／之後panic。
4. **examples（explained）**：預期輸出有條件「發布被讀到後」，沒有固定完成時間測量，不能把重跑成功當通用進度保證。

小預測：刪yield但仍Acquire讀true時，值的同步理由沒有消失，只改等待行為／耗用情況；不能推它會更快或必早結束。依本頁分工推論，未跑。

## AcqRel、SeqCst 與合法組合

1. **what（explained）**：AcqRel給RMW讀Acquire/寫Release；RMW只Acquire寫面Relaxed，只Release讀面Relaxed。SeqCst為SequentiallyConsistent：loadAcquire、storeRelease、RMWAcqRel，再加所有SeqCst atomic共同順序。
2a. **mechanism（explained）**：load只Relaxed/Acquire/SeqCst，store只Relaxed/Release/SeqCst，fetch_add五者都可。load無寫面不能Release/AcqRel，store無讀面不能Acquire/AcqRel；不合法會panic，不能只挑聽來更強名字。
2b. **why（explained）**：除了同步要求足夠，也先檢方法接受的order；單次更新和跨operation順序仍兩件事。
3. **how（explained）**：兩完整runtime-fail經函式參數傳Release load與AcqRel store，預期可編譯、執行診斷no such thing as release load／acquire-release store。這些不是compile-fail。
4. **examples（explained）**：只介紹fetch_add一種RMW，不能宣稱已會任意atomic API；未跑非法例，訊息是教材顯示。

小預測：load(AcqRel)同時有不適用寫面，不因含Acquire就合法；fetch_add(AcqRel)則符合所列RMW列。未跑。

## SeqCst 雙旗標的共同順序與反證圖

1. **what（explained）**：有限四步X/Y初0，A1寫X1/A2讀Y，B1寫Y1/B2讀X，四步全SeqCst，只這些寫。共同順序保A1<A2、B1<B2。
2a. **mechanism（explained）**：假兩load都0則A2得在B1前、B2得在A1前，A1→A2→B1→B2→A1不可能，故允許(0,1)/(1,0)/(1,1)排(0,0)。Relaxed沒有跨X/Y此共同順序保證，模型允許(0,0)，本機不必出現。
2b. **why（explained）**：展示SeqCst比各位置自己的修改序多什麼；不能擴成所有普通操作全在一直線，也不能把多次load/store合成RMW。
3. **how（explained）**：兩workers各store/load交普通值，main兩join才assert至少一1；join不重做已發生load，不將它當禁止(0,0)原因。後受控同counter五步全SeqCst仍最後1，兩load0兩store1完全可排共同序。
4. **image（explained）**：PNG「假設A、B都讀到0／四步皆SeqCst、X/Y初0」，藍A1到A2灰A內先後、紅A2→綠B1要求讀0早於其寫1、灰B1→B2 B內先後、紅左回箭頭B2→A1閉圈，底說共同序不能滿足。這是矛盾假設非實際執行軌跡；一次觀察不能證所有排程，但四步理由支持限定結果。

小預測：本例跑出(1,1)同樣合法，不表示SeqCst保證固定某worker先；兩個split read-modify-write即改SeqCst仍可能彼此讀0而兩store1，需fetch_add。後者也同頁明示，非盲發現。
