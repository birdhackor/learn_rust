## 1. 長度、hash／digest／collision 的分工

1. **是什麼（explained）**：長度不同可排除；同長度只是候選。原文hash是把任意bytes算固定長度摘要，digest是結果，collision是「不同 bytes 也可能得到相同摘要」。BLAKE3是所選演算法，blake3 crate供API，不另開平行／mmap功能。
2a. **機制（explained）**：Hasher::new無輸入狀態，update(&[u8]) mutable追加依序bytes，finalize共享借回32byte Hash而不清空／接手。Hash值有Copy/Eq/std::hash::Hash，可作map鍵；與同名Hash trait角色不同。相同bytes必相同digest，反方向不成立。
2b. **用途（explained）**：先以已有metadata大小縮小，再摘要縮小，最後真bytes確認，減少全面兩兩重讀；未承諾加速倍數。map鍵雜湊契約不證原檔相同。
3. **怎麼用（explained）**：by_size HashMap<u64,Vec<&FileRecord>>借記錄而非接手，5/5/6只留下5的兩筆。hash_reader對Read重用4096buffer、只update[..count]、Interrupted重試、其他Err直接回，0才finalize；空與非UTF8合法。
4. **例子界線（explained）**：ABC再DE與一次ABCDE同摘要，9001bytes/不同短讀上限tests驗切分無關；不會讀出相同摘要就直接宣稱重複，保存群組仍隨檔案數占記憶體。

小預測：只把ShortReader上限由3改7不改序列，digest仍同；對同一Hasher連續送ABC、DE就是ABCDE，不是兩個獨立檔的兩份摘要。未跑，前者也有同頁tests。

## 2. 比較完整序列前正規化短讀切分

1. **角色（explained）**：切分是read行為，不是內容；左右單次read得到3與1不代表內容不同。fill_chunk各自填滿相同容量或EOF才比較對應段。
2a. **機制（explained）**：filled累加，下一次借buffer[filled..]保留新前綴；Interrupted重試。slice PartialEq要求長度和每個byte相同。equal_readers每輪兩邊fill，異slice Ok(false)，相同且兩邊空才Ok(true)；CompareReadError Left/Right保存錯的來源，IO錯不是false。
2b. **用途（explained）**：消除短讀邊界差異，避免把讀不到／讀失敗當已證內容不同。
3. **用法（explained）**：泛型L/R:Read，mut借兩來源，回Result<bool,...>。ShortReader正數上限，0明定panic；failing_reader第一次Interrupted、再R、再PermissionDenied，hash/compare必傳後續失敗，不把R當完整成功。
4. **實圖（explained）**：PNG頂「同一串 bytes: ABCDE」；藍框左ABC|D|E、右A|B|C|D|E，黃框各填4格或EOF，綠框第一段ABCD=ABCD、第二段E=E。垂線是read批次非內容；箭頭是重組先後。正文補左收ABC後剩一格只能D，下段才E；實作4096非圖4。圖不保證File每次這樣交，也不代表一次read=完整內容。

小預測：左ABCDE右ABCD，首比較段相同後仍須比較下一段E與空，回false，不能在首段就true；兩空來源true。後者同頁test已見，未跑。

## 3. 真檔案的盡力觀察與確切錯誤者

1. **角色（explained）**：File::metadata查已開handle所指檔，observe查路徑；Rust共享borrow不鎖住FS其他寫入。FileIssue持原生path、action與FileCause IO／Observation／Changed。
2a. **機制（explained）**：open_checked開前observe與scan snapshot比，File::open後verify_unchanged同查path和handle；hash/compare後再查。hash_file只有讀完及後觀察成功才交digest；equal_files即使正常false也觀察後才回。讀錯Left指left原生路徑，Right指right，不一律怪新候選。
2b. **用途（explained）**：揭露可見len/modified/type差異或讀取失敗，以供caller保留精確問題。只開前查不足以覆蓋讀後變化。
3. **用法（explained）**：以FileRecord借入wrapper，成功Result<Hash>或Result<bool>，失敗FileIssue。verify_unchanged也公開給受控測試；snapshot Copy可建受控missing記錄。
4. **例子界線（explained）**：完整post-read測試先hash讀完、再fs::write改長、最後呼同helper，不是假稱每次read同步改動。原文明說非原子快照、同長同時可能改回、時間精度、查詢間路徑替換；穩定目錄整理範圍，不保證惡意替換或未來永不變。

小預測：一次前觀察已Changed便不去hash，回對應path/開啟前動作；把內容換同長而modified碰巧也相同可能觀察不出，因此不能提升保證。未跑。

## 4. Tuple 候選鍵與 fail-fast owned map

1. **角色（explained）**：`(u64,Hash)`兩欄都Eq/Hash時tuple也提供，兩欄都等才同鍵；DigestBuckets只是alias，不是newtype。
2a. **機制（explained）**：hash_candidates接手Vec<FileRecord>逐一hash，按(size,digest)放Vec，首FileIssue以?離開，不交之前半份map為完整成功。filter借owned Item判斷、collect才接手保留項。
2b. **用途（explained）**：明確表示候選條件，避免不同size進同桶，也避免中途失敗被成功容器掩蓋。
3. **用法（explained）**：candidate example自己的mod candidates，不放streams或checked-files library；固定選兩筆size5，形成一桶兩筆，仍顯示scan issues。真資料可多桶、HashMap無固定順序。
4. **例子界線（explained）**：candidates.rs兩tests實讀，AAA/AAA/BBB/AAAA成三桶、missing回Err而非partialOk；形成桶尚未判重複。

小預測：若任意兩項size同但digest不同應進不同桶；手工給相同digest也不能證相同，需下一步。未跑。

## 5. 逐組代表 refine 與借用群組

1. **角色（explained）**：ContentGroup<'a>存Vec<&'a FileRecord>，return借用連唯一input slice，來源不能先結束。每候選比較各既有組代表，全部不同才開新組。
2a. **機制（explained）**：seen HashMap<PathBuf,()>用unit當存在標記，同一路徑重複只算一次；新singleton也hash_file完整驗讀，摘要不用作其內容判準。members按path，再groups按最小path排序；callback &&FileRecord因元素本來是&FileRecord。每組有首位，空input零組。
2b. **用途（explained）**：同digest桶可能有多種內容，只比桶首會漏掉後來彼此相同的另一組。獨立元件不假設caller剛讀過。遇Err不交半份groups，caller保留問題、移除確切失敗path才可重建，其他仍可能失敗。
3. **用法（explained）**：refine_bucket(&[FileRecord])→Result<Vec<ContentGroup<'_>>,FileIssue>；報重複時才挑至少2不同path組，元件保留singleton供驗證。
4. **實圖（explained）**：藍框手工同digest a:AAA、b2:BBB、b1:BBB全3bytes；黃框b1先比a不同、再比b2相同／必須比較各組代表；綠框真群1 a，真群2 b1、b2。這是人為同鍵，不是真的找到BLAKE3 collision，也不是所有同digest三份都重複。圖顯b1/b2輸出排序，未承諾跨平台同排序。

小預測：順序B、A、B仍應形成兩內容組，最後按path排序而非到達順序；同一路徑兩次不增path_count。後者同頁test已見，不稱盲解。

## 6. 按路徑量、hard link 與 checked 算術

1. **角色（explained）**：量為(path_count-1)×len，0/1路徑或空內容為0。hard link是同一實際檔另一名字，仍按兩個路徑算，不是可回收實體空間或刪除建議。
2a. **機制（explained）**：先path_count<2回0避免減法問題，u64::try_from usize額外數可能TryFromIntError；checked_mul/checked_add超u64回None非wrap，轉MetricError::Overflow。u64::MAX是最大值constant，不需巨大檔案測。
2b. **用途（explained）**：固定指標意義並避免大數轉換／乘加回成看似正常小量。即使release開溢位檢查，這裡仍用Result政策給caller具體失敗。
3. **用法（explained）**：duplicate_bytes算組、add_duplicate_bytes安全累加。AAA singleton0、BBB雙路徑3，總3而非同digest直接6。Unix fs::hard_link(original,new_path)->ioResult為兩名字fixture，其他平台cfg不編。
4. **例子界線（explained）**：u64MAX×2和MAX+1 tests是受控算術；hardlink test兩路徑算3只證本指標，不證能釋放3磁碟bytes。TryFromIntError是標準整數轉換，非舊Count自訂錯。

小預測：三個不同path的空檔會是同內容且量仍0；len3/path_count3是6，若其中一個是重複輸入同path，應先去重而不能直接用3。未跑。
