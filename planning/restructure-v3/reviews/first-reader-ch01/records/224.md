## Thread、concurrency、parallelism

1. **what（explained）**：原文thread是程式中「能獨立推進工作的一條執行路徑」，自己的呼叫進度和stack；main起於一thread，普通函式呼叫不另建thread。concurrency是工作期間重疊，parallelism是實際同刻執行多工作。
2a. **mechanism（explained）**：OS排程給執行機會，可能交錯也可能多核心同時。既讀borrowing仍適用，另需跨thread型別契約。
2b. **why（explained）**：一條計算數列時原路徑準備別資料，先看值或reference能否交給另一方；多thread不保證更快／固定輸出順序。
3. **how（deferred）**：本頁只普通呼叫檢契約，下一節才建立／等待thread；沒有可在此照做的spawn API，尚不猜。
4. **examples（explained）**：Batch加總200只是資料正確，沒有兩thread或速度測量。沒有將一般helper當執行緒。

小預測：把計算拆兩個普通函式依序呼叫仍在當前thread，不因函式數量變成parallel。未跑。

## Send、marker／auto trait

1. **what（explained）**：Send表值可安全跨thread移交，owner移交包括清理責任；reference值移交只交借用資訊。marker trait表示性質、不像Charge提供方法；auto trait由編譯器依型別／組成判定，不是derive。
2a. **mechanism（explained）**：普通struct所有欄位Send可自動Send。Send/Sync在std::marker且預先可用；`require_send<T:Send>(value:T)->T`接手再原樣交回，只核bound，無clone／storage／thread。
2b. **why（explained）**：把型別可交接和真正建立等待工作分開檢查；不能只看業務資料，容器管理資訊也參與安全性。
3. **how（explained）**：String、i32、Vec<i32>、Box<String>有Send，Batch String+Vec也有。require_send(batch)交回新binding後可繼續借batch。
4. **examples（explained）**：完整Batch target及Cell/RefCell target證各bound與本thread計算；只讀它們沒有實際跨thread。也不推所有Vec<T>與Box<T>無條件Send，內層仍要符合。

小預測：把Batch欄位加Rc<i32>便不能只沿原本String/Vec通過推整體Send；依後面同頁Rc規則推論，非隔離解題。

## Sync、shared borrow 與實圖

1. **what（explained）**：原文精確「T: Sync 等價於 &T: Send」，關心shared reference能移交，不是移走原owner，更不憑空給mut。
2a. **mechanism（explained）**：require_sync<T:Sync+?Sized>(&T)->&T允許str DST，輸出借用連唯一輸入。String Sync因此&String Send；原borrowing／型別提供的修改介面仍管存取。
2b. **why（explained）**：分清整容器移交與保留原值、跨thread借讀；Sync不自動回答來源活多久。
3. **how（explained）**：Batch先require_sync(&batch)，回&Batch再交require_send對應等價；str版本require_sync(text.as_str())的T是str，不是&str。borrow最後使用後才move owned String。
4. **image（explained）**：圖上半threadA交String→綠箭頭→threadB接String，標ownership移交／String:Send；下半綠框threadA仍持原String，藍框threadB持&String，由藍箭頭向上借原字，標&String:Send等價String:Sync。這是允許關係，不是本頁程式真的兩thread，也無reference可超owner壽命的保證。

小預測：String通過Sync仍不能由普通&String呼要求&mut self的push_str；共享借用限制沒有取消。未跑。

## 同步、data race 與既讀容器

1. **what（explained）**：同步限制衝突操作或建立工作先後；data race是不同thread同記憶位置未同步衝突，至少一方寫。Cell/RefCell/Rc的管理狀態也是資料。
2a. **mechanism（explained）**：Cell<i32>／RefCell<i32>有Send無Sync，內T需Send；整owner交走未留下舊位置可用owner。Rc<i32>兩者皆無，clone/清理會改同份計數。RefCell guard只管理單thread借用，try_borrow或mut binding不增加Sync。
2b. **why（explained）**：不能以「只讀外部數字」忽略內部計數／借用狀態的更新，也不能將單thread合法推成跨thread合法。
3. **how（explained）**：owned Cell加一3→4、RefCell block內push後guardDrop再借和200可通Send；要求Sync的Cell/RefCell負例E0277，Rc移交也E0277。表中每種容器配的具體內T不是無條件能力表。
4. **examples（explained）**：只寫Cell.get也無法跳過Sync型別要求；即使這次Rc只有一handle也不使Rc得到Send。沒有實際製造data race程式，錯誤在編譯期契約拒絕。

小預測：Report(String,Cell<i32>)可Send不能Sync；此頁練習完整答案已見並確認同樣結論，不宣稱自己未提示獨解。若Cell換成RefCell<i32>，依同表仍Send非Sync，未跑。

## Closure 呼叫能力、Send 和 static 分別

1. **what（explained）**：move決定按值capture，Fn系列決定怎麼呼叫，Send/Sync決定跨thread使用，static決定內借用依賴；四者不互代。
2a. **mechanism（explained）**：move closure實際保存String可Send，body只讀因此可重呼Fn；保存Rc仍Rc管理資訊，E0277。`require_send_static<T:Send+'static>`另要static，局部&str可Send但不static，E0597；move保存reference也不延長原String。
2b. **why（explained）**：交接介面若排除短命外借需另外bound；不能用move或Fn名稱聲稱已安全收尾，也不能把static當永久不清理。
3. **how（explained）**：borrow_bounds先將局部view過Sync/Send並使用，後move owned text進static helper、block結束仍清理。closure require_send只回同closure，work()才讀長4。
4. **examples（explained）**：Rc closure當前thread呼叫合法，失敗的是Send要求；最後println只表示回外層，不量測Drop時刻。static來源錯誤和Send能力缺少的診斷分開；沒有據此保證所有工作已完成。

小預測：move || borrowed_view.len()若view借局部String，會把reference按值存起但仍不是static； owned String closure可static也仍會Drop。依已讀規則推論，未跑。
