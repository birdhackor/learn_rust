## 共同欄位與依賴

1. **是什麼／既讀關係（explained）**：沿既讀 workspace/package/dependency，`[workspace.package]` 是成員可採用的共同欄位；`[workspace.dependencies]` 是可採用的來源設定。原文說「只在根設定列出，不會讓所有成員自動取得library」。
2a. **機制（explained）**：`version.workspace = true` 的點號是設定層級，true 表採用共同值，並非把 version 或 edition 設成 bool。各成員明寫自己的 name，並明寫 `lesson-subtotal.workspace = true` 建立依賴。根 dependency path 從根 manifest 所在處起算，不從 app 出發。
2b. **用途（explained）**：一起維護的 package 能共用版本等欄位而保留成員的選擇責任。`rust-version = "1.99"` 宣告最低需求，不安裝或選工具鏈；publish=false 禁 Cargo 發布到 crates.io，不禁止本機執行。
3. **怎麼用（explained）**：小 workspace root 的 path=subtotal，app採用；若在 app 自寫 path 則為 ../subtotal。`--manifest-path` 先選 workspace，`-p` 再選其中 package；各 workspace 有自己的 lock/target。root exclude 入門 workspace 不會把它的 lock 混進來。
4. **例子界線（explained）**：完整兩 member manifest 和 lib 顯示共同設定不改 80×2=160 的計算；repo root 三表明說只是節錄，不能當成完整替換 manifest。沒有因此載入舊 ch01 library。

小預測：只將 lesson-subtotal 留在根表卻刪 app 的採用行，不會自動擁有該 library；此問題同頁答案也已看，不是隔離解題。把根 path 原樣搬到 app 則起點錯，會指向 app/subtotal（依相對路徑規則推論）。

## Profile 與整數檢查

1. **角色（explained）**：profile 是編譯設定組，dev 通常供 build/run，--release 選 release，與 edition/package選擇分開。
2a. **機制（explained）**：opt-level通常0–3，dev預設0、release3；根 `[profile.release] overflow-checks = true` 使超 i32 範圍的執行運算 panic，並不擴大i32。成員 profile 會被忽略。
2b. **用途（explained）**：選最佳化及保留溢位檢查，使兩種建置不因設定差別忽略超範圍；較多最佳化通常較花編譯時間，不能直接推定執行速度。
3. **用法（explained）**：根設定後加 --release；成品預設小workspace target/release。這些80、120的未超範圍運算仍得160／280。
4. **例子界線（explained）**：教材展示建置與已知答案，沒有效能量測；也沒有這頁實際超範圍範例。不能把等答案當成加速證據。

小預測：只改 opt-level 不應令同樣80×2產生不同答案；若選錯 manifest，改另一個 workspace 的profile不代表目前這份採用它。未跑。

## Package feature 與條件編譯

1. **角色（explained）**：先前選 dependency 的 derive，這次定義自己 package 的 batch。`batch = []` 沒連帶啟用項目；`default = ["batch"]` 是預設功能列表。「條件編譯」依建置條件保留／排除程式，沿既讀 cfg(test)。
2a. **機制（explained）**：--no-default-features不啟用預設列表，--features batch可再明選，--all-features選全部。不同使用者對同dependency功能通常合併，因此功能適合可同時存在的增加能力。`#[cfg(feature = "batch")]` 未滿足時函式／block根本不存在；`cfg!(...)` 僅給bool，普通if的body仍檢查名字型別，false也不移除呼叫。
2b. **用途（explained）**：可選批次介面而保留單筆，不在執行時猜可選函式是否存在。這裡命令選本package建置，與dependency default-features=false的責任不同。
3. **用法（explained）**：two_orders與呼叫block內use都掛attribute；default及no-default+features batch得160,true和280，no-default只得160,false。測試檔同樣排除batch測試，測試數2／1／2。
4. **例子界線（explained）**：故意失敗獨立程式的 if cfg! 仍引用被排除的two_orders，E0425；正確main和完整答案排除block。這不是說bool if完全無用，它可顯示條件結果。未跑rustc或Cargo，也不把同頁答案算自己隔離完成。

小預測：在no-default下只替函式加cfg、呼叫的use卻留在外面，仍會引用不存在介面；必須一併條件化。已看完整模式後的推論。

## Target／host 與檢查範圍

1. **角色（explained）**：編譯target平台是準備在哪執行，host是跑編譯工具的本機；Cargo example target則指某項建置成果，要依上下文辨別。
2a. **機制（explained）**：crate的cfg依編譯目標固定，不每次執行重測；cfg!(unix)、cfg!(target_os="windows")給目標條件。--all-targets是library/binary/examples/tests等成果，不是所有OS。
2b. **用途（explained）**：選適合目標的程式區塊，並避免把release、所有成果檢查、跨OS當成同一操作。
3. **用法（explained）**：例Linux預期unix=true/windows=false；一般未另選時host/target通常相同。release不把Linux變Windows。clippy all-targets/all-features也會編譯本頁已讀答案example。
4. **例子界線（explained）**：只列Linux輸出而明說依實際target，不保證我的機器結果，也未教如何交叉編譯。

小預測：同一個已建成程式搬移執行，不會把其中cfg!變成每次重查的結果；能否在那平台執行是本文沒承諾的另一問題。未跑。
