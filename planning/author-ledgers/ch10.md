### 四題作者自查與原承諾範圍

1. **身分／角色：**thread是執行路徑；Send是值移交，Sync等價於shared reference的Send。reference值與referent ownership不混同；marker不提供工作method，auto不是derive。
2. **機制／性質：**bound檢查實際T，helper只原樣交回；正常Batch與String closure自動符合，Cell／RefCell可Send但不能Sync，Rc及捕捉Rc的closure不能Send。static另檢查型別內借用依賴。各項先介紹後再例示。
2. **需要／用途：**原需是選擇移交或保留原資料的跨thread介面。兩個借用／owned檢查明確說明這兩種需要；Cell對照阻止把単thread的shared receiver當作可跨thread，capture對照阻止把move當作萬能補救。當下只是型別契約準備，建立／取得成果／收尾在10.2完成，不把helper當並行執行。
3. **使用／結果：**每個helper明列參數與返回；library與example路徑、Cargo命令沿既有形式。失敗fixture完整且在原因已教後出現；正常程式的200／4／2與來源操作對應，無未知API。
4. **例子／圖／證據：**圖的兩個面板分綠owner移交、藍reference指向原owner。positive編譯證據用於契約，runtime輸出只用作既有資料操作檢查；不證明已開thread、速度、無死鎖、工作已完成或所有未來使用正確。

### 四題及承諾範圍

1. **身分／角色：**spawn接手工作並建立thread；JoinHandle是唯一等待權；join接手權限並等待／取成果；thread::Result的Err持有panic資料。普通Result是工作自己回傳的判定，payload decoder是收到Err後辨認內容，不是工作重試。
2. **機制／性質：**work F與result T分別Send/static；move owned Vec移交，原名不可用，借用closure不因立刻join就符合static。join建立完成之後再使用成果的關係；unwind的panic可在thread邊界取得Err，abort不能。普通check_amount的Err仍在正常回傳路徑，因此外層Ok。drop handle detach保留worker可繼續的可能，但失去等待權。
2. **需要／用途：**原需是完整206、辨認拒絕／panic並確實收尾。主工作放在join之前允許這份獨立資料工作先推進，join是需要200時的等待點；不是為了證明兩核加速。兩層match避免把拒絕誤判成panic、把thread正常回傳誤判成金額接受。文字decoder對常規panic的兩種可能型別都處理；未知fallback只報未辨認，避免假造內容。兩handle答案先等待全部，避免報告第一份失敗時第二份被detach。
3. **使用／結果：**逐項介面均早於code；alias與selected無bodyAPI簽名標明用途。正常4targets有完整manifest既有環境及Cargo-p-example--locked commands；4fixtures全獨立Rust，expected後綴符合check-fixtures.py。作者初次漏查測試super路徑與String對&str跨型別assert，root核對後依下方記錄改成已教crate路徑與as_str同型比較；其餘cfg／Box unsizing沿actual前文。沒有scope、Arc、Mutex、channel、sleep／Duration、panic_any、catch_unwind或resume_unwind。
4. **例子／圖／證據：**200+6支持資料分工及成果合併；金額200/-1支持內外兩層Result；一次worker panic支持Err payload/main正常exit，不支持abort復原或未知型別解析。圖灰箭頭是各自流程，綠箭頭是owner／成果交接，縱向距離不測時間，跨lane並排不指定排程。兩worker答案一般執行實驗只走兩Ok；失敗也等待兩份的結論由兩次join位於match之前的已教控制流程得出，未偽稱執行了panic版答案。

### 10.7 完稿的四題自檢

1. **身分／角色：**RwLock 擁有資料並安排存取，Arc 管共享 ownership；read/write guard 各自管理已取得的權限。ReadGuard 的 Deref 只給 shared borrowing，WriteGuard 另有 DerefMut；兩種 owned guard 都沒有 Send，worker 在自己的 thread 取得、清理，只交回 owned 數值。TryLockResult 的 G 指整份 guard，非內部資料 T；WouldBlock 沒有 guard，Poisoned 含已取得的 guard。
2. **機制／性質：**read guard 可並存，write guard 不與任何其他 read/write guard 並存，最後一次使用不會因此立即 Drop。讀改寫必須釋放後重取，條件要在現在的 write guard 下重查並更新。downgrade 消耗 write guard，沒有解鎖窗口地轉成 read guard，不提供反向 upgrade；atomic 性質由官方契約支持。RwLock 的 Sync 需要 T:Send+Sync，與 Mutex 的 T:Send 條件分開；reader panic 不 poison，writer panic 可能 poison，不能由無 poison 推業務成功。
3. **原問題／收益：**每位 caller 需要自行管理同一清單的 shared view，另外 writer 獨佔更新；兩份 reader 清理完才能追加30。三項上限例讓原觀察2、另一更新後3、重查拒絕追加之間的因果清楚，不用 sleep 或假設排程。保留剛寫狀態的需求才引入 downgrade。poison 例明定三筆獨立完整數值可保留，用長度加逐項80/120/30檢查，沒有把任意資料的只讀檢查當成一般修復保證。
4. **呈現／支持：**兩份 guard 與兩次 WouldBlock 支持本次權限占用的觀察，兩份都 Drop 後230是實際更新結果；跨 thread 的200與答案230不證明 reader 本次同時執行或 RwLock 加速。重查例是同一 thread 主動安排的先後，非量測 race。downgrade 例230/270驗證呼叫結果，未競爭的程式不能證明所有交錯的 atomic 性質。兩份 panic 的 main 正常返回且 stderr 有 worker panic，分別驗 reader-only不poison與已知writer狀態檢查後清標記。fixture 驗 read guard 缺 DerefMut、Cell 缺 Sync，以及兩種不同鎖 guard 各自缺 Send，避免把同鎖衝突混入型別檢查。

### 10.8 完稿的四題自檢

1. **身分／角色：**AtomicUsize/Bool 各管理一個數值位置，shared receiver 更新沿interior mutability；SendSync支持Arc共享，不把Arcclone或load副本當作複製atomic。load讀值、store替換、fetch_add合成RMW並交舊值；ownedatomic沒Copy，移動後原binding不可再用。Ordering指定每次操作的同步契約，首例只選已介紹Relaxed，未把強度名當所有方法的合法參數。
2. **機制／性質：**同atomic修改有共同順序，RMW讀直接前值再一體更新；Relaxed本身不建立跨atomic發布關係。join完成同步使全工作後final load不能取完成前舊count。Release與讀自它的Acquire在相同flag上配對，串producer前與consumer後的HB；唯一true來源與無後續payload寫各有獨立用途。AcqRel讀Acquire/寫Release、RMW只Acquire/Release的另一側Relaxed；SeqCst另有SC操作共同順序，但不把分離load/store合體。非法loadRelease／storeAcqRel依方法契約panic。
3. **原問題／收益：**先要每件工作各加1，從Mutex整段權限接一次RMW；再要consumer看到可讀時也能讀到producer完成的230，旗標配對才連回這份需要。五次count與全部正常join分開檢查，lost_update用可控交錯反映原各加1需求沒達成。SeqCst有限四步問題本身是性質辨認，不反推效能／業務需求；以循環排除雙0。練習把一payload擴成同批長度3/總和230，兩份寫都Release前、兩份讀都Acquire後且無後寫，才能解釋完整成果。
4. **呈現／支持：**values80→200→230驗舊值與替換對象，compilefail E0382支持ownedatomic未Copy。count5驗本次兩worker工作結果，其所有次序理由先由RMW與join契約建立，沒有拿run次數作proof。兩lost_update正常例各得1，支持這份主動安排的允許先後確實沒達兩次加；SeqCst不修正此一分離更新。publication圖P1/P2/R1/R2與tuple0/1明確對應，跨箭頭限定R1讀自唯一P2才有HB；程式consumer讀230後才join，不用晚join倒替前面的load作理由。SeqCst圖是雙0假設形成矛盾的要求，非執行軌跡；真run取得(0,1)只驗允許結果之一，禁止(0,0)仍靠SC契約與循環理由。兩payload答案依相同理由讀(3,230)，不推重設flag或發布後反覆更新的協定。
