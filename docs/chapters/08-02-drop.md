# 8.2 用 Drop 觀察 ownership 的收尾

2.2 已說明：值仍由局部變數持有時，離開scope會結束這個值；若它管理資源，則依型別的規則清理。上一節的Box也有這種責任。現在想讓自己的資料在清理前做一項工作，並看清楚這項工作何時發生。

先不管理檔案或網路。我們給每份資料一個數字id，收尾時顯示它。輸出的用途是追蹤清理順序，不是模擬真正釋放記憶體的完整實作。

## Drop 是清理時要執行的自訂工作

**destructor** 是值結束時的清理動作。Rust會自動處理一個值已經擁有的欄位；如果還需要自訂工作，可以為型別實作 **`Drop` trait**。本節使用它的穩定介面 `fn drop(&mut self)`：它借用即將被清理的值，讓自訂工作讀取資料或修改需要的狀態，回傳unit。

`impl Drop for Tracked` 與4.1實作Charge的形式相同。差別是Drop的觸發由Rust管理，不是我們在一般流程中隨意呼叫method。Drop已在標準的名稱範圍中，可以直接使用；這一項自訂trait實作不需外部dependency，也不需derive。

`Tracked { id: i32 }` 是本節用來追蹤的一個簡單struct。它持有自己的id；`drop`顯示這個id，讓我們把輸出對回特定值。它沒有取得另一份owner，也沒有把自己move出去。

下列程式先建立外層id1，在內層block依序建立id2與id3，再回到外層。回來後用 `let view = &first;` 建立shared reference，透過view讀id，然後繼續顯示main結束前的文字：

```rust
--8<-- "examples/ch08-smart-pointers/examples/drop_scope.rs"
```

```bash
cargo run -p ch08-smart-pointers --example drop_scope --locked
```

```text
建立外層=1
建立內層=2、3
清理 id=3
清理 id=2
內層已收尾，外層仍是=1
main準備結束
清理 id=1
```

正常離開內層block時，其中的局部變數以宣告的反序清理，因此先id3、再id2。first由外層持有，仍能在後面讀到id1，直到main結束才清理。

這也補上2.4的重要區別：**reference最後一次使用結束，不等於owner立刻被清理。**view最後讀取後，程式還印了 `main準備結束`，持有原值的first才隨main結束清理。borrow的使用範圍與owned值的收尾位置是兩件事。

## 想提早清理，交出值給 std::mem::drop

如果工作已經結束，不想等目前scope收尾，可以用標準函式 **`std::mem::drop(value)`**。它接收owned值、回傳unit；值交進函式後，在函式返回前完成正常清理，因此呼叫者不能再使用已交出的非Copy值。

可以用前文的 `use` 引入它，之後只寫 `drop(value)`。這是普通函式呼叫，沒有 `!`，也不是直接呼叫Drop trait的method。

同樣的Tracked現在先發生move，再顯式清理：

```rust
--8<-- "examples/ch08-smart-pointers/examples/drop_early.rs"
```

```bash
cargo run -p ch08-smart-pointers --example drop_early --locked
```

```text
建立資料=1
接手資料=1
清理 id=1
清理完成後，繼續工作
```

`let second = first`轉交同一份值；不會因為first不再可用就當場清理id1。second接手後，`drop(second)`再把它交出並完成清理。main結束時也不會為同一份資料再清理一次。

2.2已介紹數字的Copy行為，因此要留意另一種情況：把i32或shared reference交給drop，傳入的是它們的副本，不會因此清理原來被借的資料。本例使用沒有Copy的Tracked，才會轉移這份值的管理責任。不要用 `drop(&value)` 當作「清理value」的寫法。

### 為什麼不能寫 value.drop()

Drop trait的 `drop(&mut self)` 只是借用receiver。若允許手動呼叫後，原值仍由呼叫者持有，之後還可能繼續使用或再次自動清理，便不能把收尾責任保持清楚。Rust因此禁止直接呼叫這項method；需要提早清理時，用接收owned值的std::mem::drop。

下面故意呼叫 `value.drop()`，會收到 `E0040`。它是編譯時拒絕，不是先成功清理後才panic：

```rust
--8<-- "examples/ch08-smart-pointers/fixtures/compile-fail/direct_drop.rs"
```

### 提早清理也要等借用用完

std::mem::drop需要接手值，仍須遵守2.4的borrowing規則。下面的view在清理後還要讀，因此值不能先交出去；這份fixture會收到 `E0505`：

```rust
--8<-- "examples/ch08-smart-pointers/fixtures/compile-fail/drop_while_borrowed.rs"
```

把最後的借用讀取放到drop之前，才能先用完借用，再交出值清理。Drop沒有把「資料要活到reference用完」的要求取消。

## 自訂 Drop 完成後，owned 欄位仍會自動清理

struct欄位也可以持有其他struct。這裡的 `Pair` 有first與second兩個欄位，型別都是Tracked；建立Pair時，把兩份Tracked交進對應欄位，由Pair擁有它們。first／second是欄位名，不是前面範例中外層的變數。

Pair也實作Drop，在自訂工作中顯示「開始收尾」。這項method結束後，Rust仍會清理它擁有的欄位；**struct欄位按照型別定義中的欄位順序清理**，和前面局部變數的反序不同。本例因此先做Pair自訂工作，再清理first的id10，最後是second的id20。

```rust
--8<-- "examples/ch08-smart-pointers/examples/drop_fields.rs"
```

```bash
cargo run -p ch08-smart-pointers --example drop_fields --locked
```

```text
建立Pair=10、20
Pair先收尾，欄位仍是10、20
清理欄位 id=10
清理欄位 id=20
```

所以一般包含String、Vec或Box的struct，不需要為了清理那些owned欄位，再寫一份重複的手動清理。型別本來就會處理自己管理的內容；Drop留給我們確實需要的額外收尾工作。這裡描述正常完成scope與std::mem::drop的流程，並不把一次輸出推成所有程式結束途徑的保證。

## 有 Drop 的值要保持完整交接

4.2為純數值struct加入了Copy，但**同一個型別不能同時實作Copy與Drop**。即使欄位全是i32，只要型別有自訂Drop，就不能再產生Copy實作；隱含複製和自訂收尾不能由同一型別一起提供。下面故意同時要求Clone／Copy與Drop，會收到 `E0184`：

```rust
--8<-- "examples/ch08-smart-pointers/fixtures/compile-fail/copy_with_drop.rs"
```

有Drop的值仍可整體move，前面的first→second就是例子。另一項限制是：**不能直接move出它的非Copy欄位**。6.2的Holder能接手後交出owned內容，是因為那個Holder沒有自訂Drop；若外層還有Drop需要執行，就不能先把其中一份owned內容拿走，留下不完整的值等待收尾。

下面的Labelled擁有String，Drop會讀它的label。main即使已擁有整個Labelled，也不能用 `let taken = value.label;` 直接取走非Copy欄位；錯誤碼為 `E0509`：

```rust
--8<-- "examples/ch08-smart-pointers/fixtures/compile-fail/move_field_with_drop.rs"
```

若工作只需要讀文字，就使用 `value.label.as_str()` 借用；若需要交出這份資料，就move整個Labelled。前面在Drop中讀id仍合法，因為i32是Copy，取得的是獨立數值，沒有把原欄位從待收尾的值中移走。

## 練習：先收尾一份，另一份繼續使用

在自己的example target建立id1與id2兩份Tracked，顯式drop第一份，再讀第二份的id，最後印出 `main準備結束`。先預測兩項清理各發生在哪裡，再跑程式。

應先看到id1清理，再看到id2仍可讀；最後的main結束才出現id2清理。不要為了取得這個順序，把第二份也一起drop，或改成只借用第一份交給drop。

完成後可對照 [完整參考程式](https://github.com/birdhackor/learn_rust/blob/main/examples/ch08-smart-pointers/examples/drop_solution.rs)，或執行 `cargo run -p ch08-smart-pointers --example drop_solution --locked`。

你已能分辨自訂Drop工作、owned欄位的自動清理與提早交出值。下一節回到「透過pointer借用裡面的值」，學習Deref的associated Target，以及前面顯式操作如何與借用式自動轉換銜接。
