## 動筆前必須處理的先備陷阱

### macro 的輸入是程式資料

14.1 先教 token：例如名稱、數字、標點是程式的構成單位；delimiter group 把括號中的 tokens 圈成一組。再教 matcher 如何接收已懂的 expression／ident，替換的是程式片段，不是已經算出的業務值。不要只把 `$x:expr` 翻譯為「變數」，導致讀者混淆一般 Rust 變數與 macro 的 metavariable。

重複語法先拆為單個匹配，再加入分隔與數量。若把同一個 expression 展開兩次，執行時也可能算兩次，應以已教的可觀察小變化檢查；hygiene 不保證只執行一次。

14.2 回收相同任務，用兩個相同文字名稱分辨 def-site 與 invocation-site，而不一次改任務與變數。`macro_rules!` 是 mixed-site hygiene；proc macro 的生成程式則需要作者特別處理路徑與名稱衝突，不能沿用「所有 macro 都會自動隔離名字」。`$crate` 的意義需先教，而且它不會繞過 privacy。

edition 2024 的 expr fragment 規則不同於更舊版，所用 edition 看 macro 定義位置。本課第一個例子不需要完整展示所有 fragment 或 const block；若採用相應變體，就先補它真正需要的概念。

### procedural macro 的小型完整範例

14.3 要先教 `[lib] proc-macro = true`、為何由另一個 crate 使用、TokenStream 與 ordinary String 的差別，才能展示入口函式。`syn::DeriveInput` 是解析後的程式描述，`quote!` 生成的是要交給另一份程式的 tokens。

優先採取有明確支援範圍的 derive，而不是忽略輸入的萬用骨架：例如若限某種 struct，就能對不支援 enum／泛型輸入給可讀診斷；若支持泛型，就需要先教所選 Generics／split_for_impl 類 API 及生成的 where clause，不能只拿到名稱後生成不完整 impl。

parse_macro_input 的失敗通報與 quote 輸出轉為 proc_macro::TokenStream 的轉換角色都要教清楚。Book 中用 unwrap 並宣稱入口必須 panic 的敘述不採用；Reference 和 syn Error 文件明確支持生成 compile_error。新增 trybuild／cargo-expand 等工具前也要教其操作契約，不能讓測試 helper 變成未教前提；現有維護 compile-fail harness 可以先核對有限 fixture。

### 公開介面的「成功」與相容性

14.4 不只問有沒有 pub；要用真正的呼叫者說出輸入範圍、回傳結果、失敗分類、是否消耗值、保留哪些資料及何時完成工作。公開 error 若用 exhaustive enum，新增 variant 可能影響呼叫者的 match；採用 non_exhaustive 或 private wrapper 時，先教其可建構／可匹配的契約與代價。

使用 API Guidelines 的 Send/Sync 建議時，必須有真實第10章前文；若14.4只取得8章前置，就先不展示尚未教的thread bound。在所有章按閱讀順序串接後，才能由當時已教知識評估跨thread需求。指南不是強制每個應用錯誤使用 Box<dyn Error> 的理由。

feature 是可啟用的公開能力；定義不等於啟用，能力合併也可能影響實際結果。不要用互斥 features 讓不同依賴者的合法選項組合無法同時建置，卻只測自己的 default 組合。

### property test 的獨立判準

14.5 先固定任務契約，再挑性質。可選已完成資料工具的「整理兩次與一次相同」「保留既定內容／次數」「已定義的格式往返」等，但每項都要檢查它是否真能抓到有意義的錯誤，不能把同一演算法換名後放進 test 當 oracle。

所有產生器的資料域、長度與數值範圍先交代。需要限制範圍才能避免 overflow，就明說約定；不可把生成不出壞資料當作一般正確性。prop_assume／filter 能拒絕材料，也可能把目標問題全部拒絕掉，初例宜直接產生有效域。shrinking 是在仍失敗且符合策略的材料中尋找較簡單案例，不等於總能找到唯一、數學最小的反例。

### Loom 與 Miri 的證據範圍

14.6 Loom 先把既有 synchronization 操作對應到模型能看見的替代型別，包含實際使用的 thread／atomic／lock／Arc 行為。官方簡短示例中有 std Arc，但官方同頁也提醒未替換操作的可觀察性有限；本課不能據此聲稱 std Arc 生命周期也完整被模型驗證。

模型要有限、可重現，不拿真正網路、檔案、隨機sleep當可控制來源。加 preemption bound 或其他剪枝時記錄它排除的探索；Loom 對弱記憶體行為有明說限制，不寫「所有硬體上的所有執行都被證明」。custom cfg(loom) 可能需要教新的 check-cfg／lint 設定，或改採已有 Cargo feature 分工；採哪種方式由root整合，不默默忽略 warnings。

Miri 使用獨立固定日期的 nightly，不改 root 的 stable1.99 工具鏈。實作前查該日期是否有 Miri component、能編譯所選 manifest／lock；本輪只研究，沒有安裝或驗證某個日期。命令中的 +toolchain、component、setup、test filter、隔離和平台限制要按實際使用逐項教，不能一份 CI 骨架用十個未教 flags。

Miri 通過只支持給定測試與執行；Loom 通過只支持選定模型及限制。unsafe 的安全契約與理由在12章建立，工具是額外觀察，不替它們補洞。

### benchmark 的工作要一樣，計時區間要明確

14.7 在示範前寫清楚兩個方案提供的同一份結果／ownership 契約、輸入大小與分布，以及這一次量測的是核心工作還是端到端成本。測試先確認等價結果，再做 release benchmark。

Criterion 所用 Criterion／Bencher／bench_function／iter、group/main macros、bench manifest 與 black_box，都先教輸入／輸出及為何此處需要。要對會修改輸入的工作採 iter_batched[_ref]，先教每輪準備與計時邊界；不能只說「把 clone 放外面比較公平」，因為某些真實介面本來就需要那份複製。

樣本不等於單次 iteration。先用幾次重複觀察解釋會有波動，再讀實際需要的輸出行；不展示整份未解釋的統計表。若要討論 confidence interval／p 值，就負責教其當下意義與限制；不打算教的統計欄位不作推理依據。環境、版本、CPU、背景負載與重複次數都會限制结論，不能一次微量測支持「所有 Rust 程式都變快」。

14.8 profile 找的是在哪裡花了多少可觀察成本，benchmark 才對指定工作量驗證前後變化。把配置次數、峰值記憶體、複製位元組和時間各自命名，不互代。新增 Vec capacity／reserve／clear 等操作前，先核對真正前文；選新 profiler 時先教安裝、啟動、圖形的軸／框／寬度與判讀方式。必要圖解宜畫垂直分階段的計時區間，讓手機也能直接看清 setup／工作／Drop 何時發生。
